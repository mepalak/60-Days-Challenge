MODULE 1 · FOUNDATION

What scope actually is

Before closures make sense, you need a working mental model of how JavaScript decides which variable a name refers to. This module builds that model from scratch.

The scope chain core concept

Every time JavaScript runs a function, it creates a fresh lexical environment — an invisible record of every variable declared in that function, plus a hidden link back to the environment it was written inside of. "Lexical" just means determined by where you typed the code, not by who called it or when.

When your code reads a variable, the engine looks in the current environment first. Not found? It follows the hidden link outward, one level at a time, until it either finds the variable or runs out of levels (a ReferenceError). This outward path is the scope chain.

scope-chain.jsrun mentally, then check module 1 exercise
const city = "Nairobi";

function outer() {
  const country = "Kenya";

  function inner() {
    const greeting = "Habari";
    // inner can see greeting, country, AND city
    console.log(greeting, country, city);
  }
  inner();
}
outer(); // "Habari Kenya Nairobi"
🏠

The apartment building analogy

Think of each function as a room in a building. A room can see everything in its own furniture (its own variables) plus everything in every room above it on the way to the lobby — because that's the path it was built through. It can never see into a sibling room on the same floor, and the lobby can't see into anyone's apartment. The path is fixed the moment the building is constructed (when you write the code), not when someone walks through it (when you call the function).

Click a ring to highlight it. Nesting = the scope chain. Inner rings see outer rings, never the reverse.

Function scope vs. block scope comparison

var only respects function boundaries — it leaks out of if blocks and loops. let and const respect block boundaries — every { } is a new scope. This single difference causes most of the "weird closure bug" moments beginners hit.

var — function-scoped

  • Visible anywhere in the enclosing function
  • Ignores if, for, while block boundaries
  • Hoisted and initialized to undefined
  • Can be redeclared without error

let / const — block-scoped

  • Visible only inside the nearest { }
  • Respects every block, including bare ones
  • Hoisted but sits in a "temporal dead zone"
  • Redeclaring in the same scope throws

⚠ Common misconceptions

"Curly braces always make a new scope for var." False — var ignores block braces entirely; only function bodies stop it.
"Scope depends on who calls the function." False — scope is lexical: fixed by where the code is written, never by the call site. That's what "closure" ultimately exploits.
"Global variables are scope-free." False — the global scope is just the outermost ring in the same chain; it's still one link, not a special exception.

MODULE 2 · CORE MECHANISM

What a closure actually is

Now the payoff: a closure is simply a function that remembers the scope it was created in — even after that outer function has finished running.

The definition, precisely core concept

A closure is the combination of a function bundled together with references to its surrounding lexical scope. Every function in JavaScript forms a closure the moment it's created — most of the time you just don't notice, because the outer scope disappears right away. Closures become visible when the inner function outlives the outer one: gets returned, stored, or passed somewhere else.

closure-basics.jsthe canonical example
function makeCounter() {
  let count = 0;         // lives in makeCounter's scope
  return function() {
    count++;                // inner fn reads/writes the SAME count
    return count;
  };
}

const counterA = makeCounter();
const counterB = makeCounter();
console.log(counterA()); // 1
console.log(counterA()); // 2
console.log(counterB()); // 1 — its own separate count

makeCounter finishes executing on line 1 of usage, yet count never gets garbage-collected — because the returned function still holds a live reference to it. Each call to makeCounter() creates a brand new lexical environment, so counterA and counterB close over two entirely separate count variables.

🫙

The firefly jar analogy

Imagine count as a firefly glowing inside makeCounter's room. Normally when you leave a room, the door shuts and whatever's inside eventually fades. But a closure is like catching that firefly in a jar and taking it with you — the returned function is the jar. Wherever that function goes, the firefly keeps glowing, still reachable, still alive, invisible to everyone except the one holding the jar.

The outer room "closes," but the firefly (variable) survives because the returned function carries a live reference to it.

Closures vs. plain functions comparison

Ordinary function call

  • Local variables die when the function returns
  • No hidden state between calls
  • Same inputs always start from the same blank slate

Function created inside another

  • Keeps a live link to the outer variables it uses
  • State persists across multiple calls to the inner fn
  • Each outer call creates an independent, private copy

⚠ Common misconceptions

"A closure copies the variable's value." False — it keeps a live reference. If the outer variable changes later, the closure sees the new value, not a snapshot.
"Only functions that return a function are closures." False — any nested function referencing an outer variable is a closure, whether it's returned, passed as a callback, or attached to an event.
"Closures need a special keyword." False — closures are automatic and free; there is no closure keyword, they're just how JS functions always behave.

✅ Key takeaways

  1. A closure = a function + a live reference to the scope it was defined in.
  2. Every function forms a closure; it's only visible once it outlives its creator.
  3. Closures hold references, not copies — changes to the outer variable are visible.

MODULE 3 · PRACTICAL APPLICATION

Using closures on purpose

Closures aren't a party trick — they're the mechanism behind private state, factory functions, memoization, and the loop bug that trips up nearly every JS developer at least once.

Pattern 1: private state application

Before #privateFields existed in classes, closures were the only way to get true privacy in JavaScript — a variable that literally cannot be reached from outside, only through functions you explicitly expose.

bank-account.js
function createAccount(initialBalance) {
  let balance = initialBalance; // unreachable from outside

  return {
    deposit(amount) { balance += amount; return balance; },
    withdraw(amount) {
      if (amount > balance) throw new Error("Insufficient funds");
      balance -= amount; return balance;
    },
    getBalance() { return balance; }
  };
}

const acc = createAccount(100);
acc.deposit(50);      // 150
acc.balance;               // undefined — truly private

Pattern 2: function factories application

function-factory.js
function multiplyBy(factor) {
  return (n) => n * factor; // closes over "factor"
}

const double = multiplyBy(2);
const triple = multiplyBy(3);
double(5);  // 10
triple(5);  // 15 — independent closures, same factory

Pattern 3: memoization application

memoize.js
function memoize(fn) {
  const cache = new Map(); // captured, private cache
  return function(arg) {
    if (cache.has(arg)) return cache.get(arg);
    const result = fn(arg);
    cache.set(arg, result);
    return result;
  };
}

The classic loop bug debugging

This is the single most common closures interview question, because it directly tests whether you understand var vs let from Module 1 combined with closures from Module 2.

Buggy — var

  • for (var i=0;i<3;i++)
  •   setTimeout(()=>console.log(i))
  • // logs 3, 3, 3

Fixed — let

  • for (let i=0;i<3;i++)
  •   setTimeout(()=>console.log(i))
  • // logs 0, 1, 2

With var, there is only one i for the entire loop — every callback closes over that same shared box, and by the time the callbacks run, the loop has already finished and i is 3. With let, the engine creates a fresh binding of i for every iteration, so each callback closes over its own snapshot.

📮

The mailbox analogy

var i is one shared mailbox that every callback has the address to — by the time anyone checks it, it holds whatever was last put in. let i gives every loop iteration its own mailbox with its own address, so each callback reads the value that was there when it was made.

⚠ Common misconceptions

"The loop bug is a bug in JavaScript." Not exactly — it's var behaving exactly as function-scoped, working as designed. let was added partly to make the intuitive behavior the default.
"Closures cause memory leaks by default." Overstated — closures keep referenced variables alive only as long as the closure itself is reachable. It's a leak only if you keep closures around longer than you need them.

✅ Key takeaways

  1. Closures enable true private state without classes.
  2. Factory functions return closures customized by their arguments.
  3. Memoization uses a closed-over cache to skip repeat work.
  4. The var-loop bug happens because one shared binding is captured by every callback; let or an IIFE gives each iteration its own binding.
MODULE 4 · MASTERY

Scope, closures, and the engine underneath

The final layer: how the module pattern uses closures at scale, what actually gets kept alive in memory, and how to reason about closures the way a senior engineer does in a code review.

The module pattern architecture

Before ES modules existed, teams simulated modules with a single closure: an IIFE that returns an object of public methods while keeping helpers and state private inside its scope. Native import/export now does this at the file level, but the underlying idea — one closure, a curated public surface — is identical.

module-pattern.js
const CartModule = (function() {
  let items = []; // private to the whole module

  function total() {
    return items.reduce((sum, i) => sum + i.price, 0);
  }

  return {
    add(item) { items.push(item); },
    getTotal: total,
    count: () => items.length
  };
})();

CartModule.add({ price: 20 });
CartModule.getTotal(); // 20 — items is never exposed directly

What actually stays in memory under the hood

Modern engines don't naively keep an entire outer scope alive just because one inner function exists — most engines (V8 included) perform closure optimization: they keep alive only the specific variables the inner function actually references, not the whole environment. Understanding this matters for two practical reasons: predicting memory behavior, and knowing that "closures are expensive" is mostly a myth for normal usage patterns.

Naively kept alive (misconception)

  • Entire outer function's variable set
  • Every argument passed to the outer function
  • Any large object created but unused by the inner fn

Actually kept alive (reality)

  • Only the specific variables the inner function references
  • Released once no closure references them anymore
  • Sibling closures over the same scope can share one environment
Only referenced fireflies (a, b) survive. Unreferenced big gets collected even though it's in the same lexical scope.

Reading closures like a senior engineer mastery mindset

When reviewing unfamiliar code, ask three questions in order: (1) Does this inner function reference any variable it doesn't declare itself? (2) Does the inner function get returned, stored, or passed elsewhere, so it outlives its creator? (3) If both are true, what is the captured variable's lifecycle — is it meant to be shared across calls (state) or fresh per call (an argument)? Ninety percent of closure bugs come from question 3 being answered wrong.

✅ Key takeaways

  1. The module pattern is one closure exposing a curated public API.
  2. Engines only retain the specific variables a closure actually references.
  3. "Closures are slow/leaky" is mostly a myth for typical usage.
  4. Diagnose closure bugs by asking what's captured and whether it should be shared or per-call.

Summary notes printable

Scope determines where a name can be seen; closures determine whether that name keeps existing after its creator returns. Every JS function is a closure over its lexical scope, but the concept only becomes visible — and useful — when an inner function is returned, stored, or handed off, letting it carry captured variables anywhere it goes. Master this and private state, factories, memoization, and the infamous loop bug all become special cases of one idea rather than four things to memorize separately.
